Introduction

What is Hustle Dev Tools?

A workflow enforcement system for Claude Code that ensures consistent, high-quality development through structured phases.

The Problems It Solves

Outdated Documentation

The Issue

AI uses training data months or years old. APIs change constantly with new endpoints and deprecated parameters.

Why It Matters

Your implementation breaks on day one. The AI confidently writes code for endpoints that no longer exist.

Memory-Based Drift

The Issue

Even after researching docs, AI "forgets" by implementation time and falls back to training patterns.

Why It Matters

Research is wasted. The AI reads correct docs, then writes code based on stale memory instead.

Self-Answering Questions

The Issue

AI asks "What format?" then immediately answers itself with assumptions. Your requirements never get captured.

Why It Matters

You end up with someone else's preferences baked into your code instead of what you actually need.

Context Dilution

The Issue

In long sessions, early decisions fade from context. By implementation, the AI has "forgotten" what you agreed on.

Why It Matters

Turn 47 doesn't remember Turn 3. That caching strategy you specified? Gone. Replaced with defaults.

Skipped Verification

The Issue

AI claims "done!" without checking if implementation matches documentation. Memory-based errors slip through.

Why It Matters

Tests pass but API fails in production. The code works for the wrong version of the API.

No Enforcement

The Issue

Nothing FORCES the AI to follow the workflow. It can skip steps whenever convenient or when context is lost.

Why It Matters

Workflows become suggestions. Without hard blocks, the AI takes shortcuts that cause rework.

Philosophy

Why 14 Phases?

The phases map to the scientific method - observe, research, hypothesize, experiment, analyze, refine, publish.

Conditional Execution

Not every task needs all 14 phases. The system is registry-aware:

Skip Research

If registry has fresh pattern (< 7 days) for similar task, phases 3-5 are skipped.

Verify Only

If artifact exists with same checksum, skip to verification phases only.

Skip Refactor

If quick fix (< 50 lines) passes review, phase 12 is skipped.

Core Workflow

The 14-Phase Workflow

Each phase is enforced by Python hooks that BLOCK progress until requirements are met.

Clarify

Phases 1-2: Understand what we're building

Scientific Method: OBSERVE
Phase 1

Disambiguation

Clarify ambiguous terms before proceeding.

disambiguation-gate.py 
User: "Create a Stripe checkout"

Claude asks: "Which Stripe checkout approach?
  A) Stripe Checkout (hosted page) ← Recommended
  B) Stripe Elements (embedded form)
  C) Custom integration"
What Gets Checked
  • All ambiguous terms identified
  • User confirms specific approach
  • No assumptions made by Claude
State Fields Tracked
phases.disambiguation.term
phases.disambiguation.user_choice
Phase 2

Scope Definition

Define what's in/out of scope.

scope-gate.py 
{
  "scope": {
    "in": ["Create checkout session",
          "Handle success/cancel redirects"],
    "out": ["Subscription management",
           "Invoice handling"],
    "success_criteria": ["User can complete
                         purchase"]
  }
}
Scope Requirements
  • Explicit "in scope" items defined
  • Explicit "out of scope" exclusions
  • Success criteria established
  • User confirms scope document

Phase 4

Interview

Questions DERIVED from research findings.

Build

Phases 8-9: TDD with isolated subagent contexts

Scientific Method: EXPERIMENT
Phase 8

TDD Red

Write FAILING tests BEFORE any implementation.

tdd-gate.py 
$ pnpm test:run

FAIL checkout.test.ts
  ✗ creates checkout session with valid items
  ✗ returns 400 for empty cart
  ✗ handles webhook events correctly

3 tests failed (expected - this is TDD Red)
TDD Red Requirements
  • Tests must FAIL initially
  • Cover all interview decisions
  • Test discovered parameters from research
  • Include error cases from docs
Subagent Used
test-writer (Sonnet - isolated context)
Cannot see implementation code
Phase 9

TDD Green

MINIMAL code to pass tests.

verify-green.py 
$ pnpm test:run

PASS checkout.test.ts
  ✓ creates checkout session with valid items
  ✓ returns 400 for empty cart
  ✓ handles webhook events correctly

3 tests passed
→ Triggering Phase 10: Verify
TDD Green Rules
  • Write MINIMAL code to pass tests
  • No premature optimization
  • Interview decisions in comments
  • When tests pass → triggers Phase 10
Subagent Used
implementer (Sonnet - isolated context)
Sees ONLY failing test file

Verify

Phases 10-12: Compare results, review, and refine

Scientific Method: ANALYZE + REFINE
Phase 10

Enforcement

All 17 Hooks Explained

Python hooks that use exit code 2 to BLOCK progress until requirements are met.

Gate Hooks (6)

Block code changes until phase requirements met

research-gate.py

Blocks Edit/Write/MultiEdit until research phase complete. Checks state.json for phases.research.complete.

interview-gate.py

Blocks until interview complete. Detects self-answering and requires human confirmation.

schema-gate.py

Blocks until schema file exists and matches research findings. User must approve schema.

tdd-gate.py

Blocks implementation until tests exist AND fail. Prevents writing code before tests.

verify-gate.py

Blocks completion until verification passes. Re-fetches docs and compares to implementation.

docs-gate.py

Blocks until documentation complete. Registry entry, OpenAPI spec, TypeDoc all required.

State Hooks (3)

Manage workflow state and context

state-manager.py

Updates state.json after each action. Tracks phase progress and checkpoints.

registry-manager.py

Updates registry.json when artifacts created. Auto-categorizes based on file path.

session-manager.py

Injects context at session start. Loads current phase, registry stats, and git status.

Quality Hooks (3)

Ensure code quality and formatting

format.py

Auto-formats after Edit/Write using Prettier. Runs on .ts, .tsx, .js, .jsx files.

code-review.py

Triggers AI review after implementation. OWASP security scan, pattern validation.

visual-qa.py

Triggers screenshot testing for UI components. Playwright screenshots at 7 viewports.

Autonomous Hooks (2)

Enable autonomous operation with Ralph Wiggum pattern

ralph-loop.py

Stop hook that forces continuation until done. Exit code 2 blocks stopping and feeds stderr back to Claude.

auto-answer.py

Selects "(Recommended)" options automatically in autonomous mode. Speeds up unattended workflows.

Context Hooks (2)

Maintain context and prevent drift

reground.py

Re-injects interview decisions and current phase every 7 turns. Prevents context dilution.

capacity-warning.py

Warns at 50/75/90% context capacity. Suggests checkpoint creation when nearing limit.

Notification Hook (1)

Alert user when input needed

notify.py

NTFY push notification when Claude is waiting for input. Enables walk-away workflows.

Specialization

All 6 Subagents Explained

Isolated context windows for specialized tasks. Prevents the LLM from "cheating" on TDD.

Orchestrator

Sonnet

Coordinates workflows, manages state, delegates to specialized subagents

Tools: All tools + Task (to spawn subagents)

Phases: All (coordination)

Researcher

Haiku

Gather documentation before implementation

Tools: WebSearch, WebFetch, Context7, Read, Grep

Phases: 3, 4, 5 (research phases)

Builder

Sonnet

TDD implementation with isolated context

Tools: Read, Edit, Write, Bash (npm test)

Phases: 8, 9, 12 (TDD phases)

Reviewer

Sonnet

Code review, security scan, pattern validation

Tools: Read, Grep, Glob, Bash (linting)

Phases: 10, 11 (verification phases)

Docs Generator

Haiku

Generate documentation, update registry

Tools: Read, Write, Glob

Phases: 13 (documentation phase)

Visual Analyzer

Haiku

Screenshot testing, visual regression detection

Tools: Playwright MCP, Read

Phases: Visual QA (UI workflows only)

Why Isolated Subagents Matter

The Problem: If Claude writes tests and implementation in the same context, it "cheats" by designing tests around what it plans to implement.

Phase 8: TDD Red

test-writer subagent

Sees: Schema, research, scope

Cannot see: Any implementation code

Writes: Comprehensive failing tests

Phase 9: TDD Green

implementer subagent

Sees: ONLY the failing test file

Cannot see: Research, interview, schema rationale

Writes: Minimal code to pass tests

Phase 12: Refactor

refactorer subagent

Sees: Passing tests + implementation

Goal: Improve without changing behavior

Rule: Tests must stay green

Resume Sessions
